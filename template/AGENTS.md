# 開発の流れ

変更の理由と検証結果を後から追えるよう、Issue・計画・PR を 1 対 1 で対応させる。

1. 作業は Issue から始める。1 つの Issue は 1 つの PR で実装・検証・文書更新まで完結させ、大きければ子 Issue に分ける。Issue どうしの依存関係は本文の `Blocked by` に書き、着手前に先行 Issue が閉じているか確かめる。
2. ユーザが承認するのは Issue と PR の 2 か所。認識のずれは、起票の前に完成イメージ（モックアップ・図・プロトタイプ）を見せて潰す。文面だけでは完成像が伝わらないため。
3. 実装の前に `docs/plans` のテンプレートに従って計画を書く。合意は待たない（Issue の承認が前提）。設計判断は理由とともに計画に残し、計画から外れたら、その変更と一緒に計画も直す。
4. 受け入れ条件を検証した結果を添えて、Issue を閉じる PR を出す。main へは直接 push せず、squash マージする。

手順は 3 つの Agent Skill にしてある。判断の仕方がセッションごとにぶれないようにするため、いずれも手動で起動する。Claude Code は `/スキル名`、Codex は `$スキル名` を使う。正本は `ai/skills/` に置き、Claude Code は `.claude/skills`、Codex は `.agents/skills` のシンボリックリンクで同じ内容を読む。

- `/create-issue <やりたいこと>` / `$create-issue <やりたいこと>`: 調査と質問、完成イメージの提示、承認後の起票。
- `/implement-issue <Issue 番号>` / `$implement-issue <Issue 番号>`: 調査・計画・実装・検証・PR 作成。
- `/review-pr <PR 番号>` / `$review-pr <PR 番号>`: レビューと修正、`docs/plans/issue<N>/report.html` へのレポート。実装したセッションの死角を避けるため、実装とは別のセッションで実行する。

置き場所を名前から推測できるよう、コードは技術スタックごとに分ける: `backend`、`frontend`、`infra`（環境の構築とデプロイ）、`packages`（配布するライブラリ）、`examples`。まだ無いものは、必要になったときに作る。

- 依存はルートで一括管理し、独自の依存を持つ部分が増えたら workspaces に分ける。

# ドキュメント

`docs` は読み手の目的ごとに分ける。

- `architecture`: 現在の設計の正本。コードと食い違わないよう、設計が変わる変更は同じ PR で更新する。
- `operations`: セットアップ、デプロイ、運用の手順。クローン直後はここの初回セットアップ手順に従う。
- `plans`: Issue 単位の作業文書（起票前の完成イメージ、計画、調査、検証記録、レビューのレポート）。親・子を問わず、その Issue 自身の番号のフォルダにまとめる。

# タスクの実行

- タスクはなるべく、Opus / Sonnet クラスのモデルで effort を high 以上にしたサブエージェントに委譲する。名前付きのサブエージェント（正本は `ai/agents/`。Claude Code は `.claude/agents` のシンボリックリンクで読み、Codex 用の `.codex/agents/*.toml` は `node ai/gen-codex-agents.mjs` で生成する）の `researcher`（調査）・`implementer`（設計判断を伴う実装）・`implementer_lite`（手順が明確な実装）・`reviewer`（差分と検証結果の確認）を使い、実行手順が明確な指示を渡す。Codex のサブエージェントは、Opus に GPT-6 Astra、Sonnet に GPT-5.6 Sol を対応させ（対応表は `ai/gen-codex-agents.mjs`）、reasoning effort は high 以上にする。最終成果物の品質はメインセッションが責任を持つ。
- 技術スタックや API の仕様は記憶で書かず、公式ドキュメントで最新情報を確認し、参照 URL とバージョンを示す。
- 不要な機能追加・リファクタ・抽象化はしない。動く最もシンプルな実装を選ぶ。
- 報告は結論を最初に書き、未検証の事項は「未検証」と明示する。悪い結果も出力ごと報告する。
- 画面やドキュメントなど人が読む成果物は、経緯を知らない初見の読み手が短時間で理解できるよう、推敲してから提出する。
