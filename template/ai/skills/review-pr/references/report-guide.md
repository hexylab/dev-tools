# レポートの書き方

`assets/report-template.html` を埋めるときに読む。

## 読み手

読み手はユーザ 1 人。コードベースを把握しておらず、レビューのやり取りも読んでいない。知りたいのは「この PR をマージしてよいか、自分は何をすればよいか」だけ。

レポートは作業の記録ではなく、その判断に必要な情報を初見で分かる順に置いたもの。差分を除いた本文は **5 分で読める量**（1,500〜2,500 字）に収める。詳しく見たい人のための差分は、折りたたんで添える。

## テンプレートの埋め方

1. `{{…}}` を実際の内容に置き換える。中の文言は、そこに書く内容の説明。
2. `T: 繰り返す` の塊は件数分だけ複製する。`T: 任意` の塊は、使わなければ塊ごと消す。
3. `<!-- DIFF:名前 -->` は `scripts/diff-html.mjs` で差分に置き換える（次の節）。
4. `T:` で始まるコメントをすべて消す。
5. 章の順序・id・CSS は変えない。見た目を毎回同じにして、読み手の負担を下げるため。

## 差分の入れ方

差分は手で HTML にせず、`review-pr` スキルのディレクトリにある `scripts/diff-html.mjs` で変換する。ファイルごとの折りたたみ（閉じた状態）になり、各行に行番号（追加行と変わらない行は変更後、削除行は変更前）と `+` `-` が付く。

**第 3 章: 変更のまとまりごとの差分。** 比較元から対象コミットまで（マージされる内容そのもの）を、まとまりに属するファイルだけ渡す。指摘のある行には `--note` で印を付ける。印は第 5 章の指摘へのリンクになる。

対象コミットは、レポートを作る時点の HEAD（修正コミットを含む、マージされる内容）。レビュー開始時のコミットではないので、差分を作る直前に `git rev-parse --short HEAD` で取り直し、ヘッダとフッタの SHA もこの値にする。

```sh
BASE=$(git merge-base origin/<base> HEAD)
git -c core.quotePath=false diff $BASE HEAD -- backend/src/invite backend/migrations \
  | node <スキルのディレクトリ>/scripts/diff-html.mjs --into docs/plans/issue<N>/report.html --slot changes-1 \
      --note 'backend/src/invite/resend-limit.ts:24:F1:期間を渡さず全期間を数えていた（修正済み）'
```

- `--note` は `<パス>:<変更後の行番号>:<指摘の番号>:<要約>`。削除された行を指すときは `-<変更前の行番号>`。
- 修正済みの指摘は、修正後の該当行を指す。差分に無い行を指すとエラーになるので、行番号を差分で確かめる。
- 変更されたファイルは、すべていずれかのまとまりに出す。どこにも出ない変更があると、読み手は差分を信用できない。ロックファイルや生成物だけは差分を渡さず、まとまりの説明にファイル名を書く（「ほかに `package-lock.json` を更新」）。
- 1 ファイルの表示が 400 行を超えた分は自動で省略される（指摘の印があるファイルは省略されない）。

**第 5 章: 指摘ごとの修正の差分。** 修正コミットをそのまま渡す（1 指摘 1 コミットなので、その指摘の修正だけになる）。

```sh
git -c core.quotePath=false show <修正コミット> --format= | node <スキルのディレクトリ>/scripts/diff-html.mjs --into docs/plans/issue<N>/report.html --slot fix-f1
```

## 全章に共通すること

- **内部の呼び名を、読み手の言葉に直す。** 識別子は括弧で添える。
  - 悪い: `InviteResendLimiter` の `window` が `Date.now()` 基準になっていない
  - 良い: 再送の回数を数えるとき、24 時間という期間を渡していない（`resend-limit.ts` の `countResends`）
- **専門用語は初出で 1 回だけ説明する。** 説明に 2 文以上かかる用語は、使わずに書き直す。
- **事実と推測を分ける。** 実行した出力があるものだけを「合格」とし、それ以外は「未検証（理由）」。推測は「未確認: 〜」と書く。
- **数を合わせる。** 結論の数値、各章の件数、表の行数を一致させる。
- **外部へリンクしない、外部から読み込まない。** Issue と PR は番号（`#34`）、証跡は `validation.md#a1` のような相対リンク。スクリプト・Web フォント・外部画像も使わず、単一の HTML で完結させる。

## 章ごとの書き方

### 結論（`summary`）

ここだけ読んでマージを判断できるようにする。

| 判定 | 選ぶ条件 |
| --- | --- |
| マージ可 | 未解決の指摘が無く、受け入れ条件がすべて「合格」 |
| ユーザの作業待ち | 指摘は片づいたが、ユーザしか実行できない検証や判断が残っている |
| 未解決あり | 修正しなかった指摘がある |

- 結論の文は 1〜2 文（80〜160 字）。合否 → 残っているもの → 何をすればマージできるか、の順。周回数や調査の苦労は書かない。
- 「あなたに残る作業」は、作業ごとに **何をするか（命令形）→ なぜ必要か（1 文）→ コマンド**。コマンドは貼って動くものだけを書き、秘密の値は `<1Password の値>` のように置き換える。

### 1. このチケットは何か（`ticket`）

200〜400 字。Issue の丸写しではなく、読み手の言葉で書く。

- **困っていたこと**: 誰が、何をしようとして、どう困るのか。原因ではなく症状から。
- **どうなれば解決か**: Goal を 1 文で。
- **決めたこと**: 実装方針のうち、知らないと以降の章が読めないもの（上限値、返すステータス、対象範囲など）。

Acceptance Criteria は第 4 章に出るので、ここには書かない。

### 2. 全体の中でどこを変えたか（`where`）

図が主役。テンプレートの部品（箱・矢印・NEW の印）を複製して描く。

- 箱 1 つが部品 1 つ（サービス、テーブル、画面、外部サービス）。2 行で「名前」と「役割」。
- 箱は 6 個まで。超えるなら粒度を上げる（テーブル 3 つを「D1」にまとめる、など）。
- **変更していない部品も 1 つ以上描く。** 変更範囲は、変わらなかったものと並べて初めて伝わる。
- 矢印のラベルは箱と重ねない。入らなければ `text-anchor="end"` で矢印の手前に置くか、ラベルを削る。
- 凡例は消さない。

図の下に 2〜3 文で、**何を変えたか**と**何を変えていないか**を書く（例: 「メール送信そのものと、ログインの流れには手を入れていません」）。

| 変更の種類 | 図の型 |
| --- | --- |
| 部品・テーブル・依存の追加 | 構成図（テンプレートの形） |
| 処理の順序・条件の変更 | 左から右へのデータの流れ。分岐は矢印を 2 本にしてラベルを付ける |
| 画面の遷移や状態の変更 | 状態を箱、操作を矢印のラベルにした遷移図 |
| 文書・設定だけの変更 | 図を省き、どの文書のどの節をなぜ直したかを 3 行以内で書く |

### 3. 変更の内容と差分（`changes`）

変更を **2〜5 個のまとまり**に分ける。まとまりはファイル単位ではなく、読み手にとっての意味の単位。

- **見出し**: 何をしたかを、動きのある一文で（「上限の実装」ではなく「再送の回数を数えて上限で止める」）。
- **なぜ**: 他の選び方があったのに、なぜこれにしたのか。これが無いと、読み手はコードの妥当性を判断できない。
- **差分**: 上の「差分の入れ方」のとおり。
- **画面の変更**: モックアップと実装を、同じ幅・同じ高さで並べる（撮り方は下の節）。

### 4. 受け入れ条件と検証結果（`acceptance`）

- Issue の Acceptance Criteria を、1 行 1 件でそのまま転記する。統合も省略もしない。
- 証跡は `validation.md` の該当箇所への相対リンクに、裏づける事実を一言添える（「テスト 8 件成功」）。
- `未検証` の行には、理由と、コマンドが結論の「あなたに残る作業」にあることを書く。

### 5. 指摘と修正（`findings`）

載せるのは、採用した指摘と、ユーザが気にしそうな不採用の指摘だけ。

- **見出し**: 起きることを書く（「バグがある」ではなく「招待ごとに累計 3 回で、以後ずっと再送できなくなる」）。
- **対象**: 第 3 章のどのまとまりか（リンク）と、ファイルと行。行番号だけでは、読み手は位置が分からない。
- **何が問題か**: 現象 → 影響 → なぜ検出できていなかったか。
- **指摘した時点のコード**: 該当箇所を 10 行以内で抜粋し、問題の行を `<mark>` で囲む。`<` `>` `&` は `&lt;` `&gt;` `&amp;` に直す。
- **未解決**: 直さなかった理由（判断が必要 / Acceptance Criteria の変更が必要 / 3 周で収束しなかった）を必ず書く。判断が必要なものには、選択肢とそれぞれの結果を添える。

| 重大度 | 目安 |
| --- | --- |
| 重大 | 受け入れ条件を満たさない、データが壊れる、認証・権限が抜ける、従量課金になる |
| 中 | 特定の条件で誤動作する、利用者が意図を誤解する、手順違反（設計文書の未更新、証跡なし） |
| 軽微 | 直せば良くなるが、動作と判断には影響しない |

指摘が 0 件のときは、テンプレートの「採用した指摘はありません」のカードにする。空欄だと、レビューしていないのか問題が無かったのか区別できない。

### 6. 残っていること（`remaining`）

3 つの区分（未解決の指摘 / 未検証の項目 / 後続の Issue にすること）は消さず、該当が無ければ「なし」と書く。各項目は 1 行。結論の「あなたに残る作業」と食い違わせない。

GitHub への投稿・返信・resolve が失敗したときは、「未検証の項目」に、失敗した操作と理由を 1 行ずつ書く（例: 「F1 のスレッドの resolve に失敗（HTTP 502）。PR の画面で Resolve conversation を押す」）。レポートにあって PR の画面に無いものを、読み手が知る手段はここだけ。

## スクリーンショット

撮るのは、画面の変更があり、ブラウザを操作する手段（Playwright など）があるときだけ。無ければ `shots` の塊を消し、文言と状態を表で示す。

1. 幅 1200px で、**対象の要素だけ**を撮る。モックアップと実装は同じ幅・同じ高さで撮る。
2. 幅 640px 以内に縮めて圧縮する（1 枚 200KB 以内、レポート全体で 1MB 以内）。

   ```sh
   sips -Z 640 shot.png --out shot-small.png
   sips -s format jpeg -s formatOptions 70 shot-small.png --out shot.jpg
   ```

3. data URI にして `img` の `src` に入れる（外部ファイルを参照すると、レポート単体で開けなくなる）: `printf 'data:image/jpeg;base64,'; base64 -i shot.jpg`
4. `alt` には、写っているものではなく、そこから分かることを書く（「上限に達して押せなくなった再送ボタンと、残り回数の表示」）。

## 提出前の確認

- `grep -nE '\{\{|<!-- (T|DIFF):' report.html` が何も返さない（埋め残しが無い）。
- `grep -nE '<script|<link|<iframe|@import|prefers-color-scheme|(href|src)="https?://' report.html` が何も返さない（単一の HTML で完結し、外部へリンクせず、配色を固定している）。
- 1 つ目は、差分の中のコード（JSX の `{{` など）に一致した分は構わない。差分の中の検査語は `diff-html.mjs` が文字参照（`&#64;import` など）に直すので、2 つ目が一致したときは、差分以外の箇所に原因がある。
- 結論だけで、判定と残る作業が読める。
- 数（合格数、指摘件数、修正済み、未解決）が全章で一致している。
- 内部の呼び名や略語が、説明なしで出ていない。
- ブラウザを操作できるなら、幅 1200px と 600px で開いて崩れが無いこと、差分が開閉できること、指摘の印から第 5 章へ移れることを確かめる。
