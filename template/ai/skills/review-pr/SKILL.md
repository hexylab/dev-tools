# review-pr

引数: $ARGUMENTS

Issue を閉じる PR をレビューし、採用した指摘を修正して、結果を 1 枚の HTML レポートにまとめる。

目的はレビューを終えることではなく、**ユーザがマージの判断に必要な情報を、自分で集めずに受け取れること**。ユーザはコードベースもレビューの経緯も把握していない。レポートが初見で伝わらなければ、指摘を何件出しても価値は出ない。

## 実行環境

- `$ARGUMENTS` は、起動時にスキル名の後ろへ続けた文字列。Codex では展開されないので、ユーザの入力から同じものを読む。
- `references/`・`assets/`・`scripts/` は、この `SKILL.md` のあるディレクトリ（`ai/skills/review-pr/`）から辿る。
- サブエージェントは、名前付きのもの（`reviewer`・`researcher`・`implementer`）が無ければ汎用のものを使う。モデルと effort は `AGENTS.md`「タスクの実行」に従い、別の CLI を起動して委譲することはしない。
- レビューと読み手テストは、会話履歴を引き継がない新規コンテキストで行う。その手段が無い環境では、未実施とその理由をレポートと報告に書く。

## 引数

- **PR 番号**。省略されたら `gh pr view --json number -q .number` で現在のブランチの PR を調べ、見つからなければユーザに尋ねる。推測で対象を決めると、無関係な PR を書き換えてしまう。
- **`--comment`**。付いているときだけ、指摘を PR のコメントとして投稿する。ユーザが目を通す前に、外から見える記録を増やさないため。

## 1. 対象をそろえる

1. `git status --short` が空であることを確かめる。未コミットの変更があれば、修正と混ざるのでユーザに確認する。
2. `gh pr view <PR> --json number,title,body,headRefName,baseRefName,files,commits` で PR を読む。
3. 本文の `Closes #N` から Issue 番号 N を取る。無ければブランチ名 `issue-<N>-<slug>` から取る。どちらからも取れなければ、1 Issue = 1 PR の手順違反として指摘に加え、N はユーザに尋ねる。
4. `gh issue view <N> --json title,body` と、`docs/plans/issue<N>/` の `plan.md`・`validation.md` を読む。`plan.md` の 2 つの表（「課題と目的への対応」「受け入れ条件の検証」）が、あとの照合の基準になる。
5. `gh pr checkout <PR>` でブランチに移り、対象コミット（`git rev-parse --short HEAD`）と比較元（`git merge-base origin/<base> HEAD`）を記録する。レポートに、どの状態を見た報告かを書くため。
6. `git diff <比較元> HEAD --stat` で変更の範囲をつかむ。

守るべき手順の正本は `AGENTS.md`、`docs/plans/TEMPLATE.md`、`.github/pull_request_template.md`、`.github/ISSUE_TEMPLATE/*.yml`。必要なときに読む。

## 2. レビューを委譲する

**自分でレビューしない。** 新規コンテキストの `reviewer`（読み取り専用）に委譲する。バグの検出には、使える環境なら `code-review` スキルも使う（`code-review` に `--comment` を渡さない。PR に直接コメントされてしまう）。

渡すもの: PR 番号と差分の範囲、Issue の本文、`plan.md` の 2 つの表、`validation.md`、下の観点。**自分の見立ては渡さない**（「ここは問題ないはず」と書くと、そのとおりの答えが返る）。

| # | 見るもの | 理由 |
| --- | --- | --- |
| 1 | バグ。境界条件、エラー処理の抜け、呼び出し元への影響 | マージ後に直すほうが高くつく |
| 2 | Issue の Problem / Goal / Acceptance Criteria、`plan.md` の 2 つの表、実装の三者が一致しているか | 途中で範囲がずれると、承認した内容と違うものが入る |
| 3 | 受け入れ条件の証跡が主張を裏づけているか（「合格」なのに証跡が無い、出力が主張と合わない、テストが条件の一部しか試していない） | 検証の主張が空だと、受け入れ条件が意味を失う |
| 4 | 設計が変わったのに `docs/architecture/` が同じ PR で更新されていない | 設計文書が正本でなくなる |
| 5 | この Issue と無関係な変更（ついでのリファクタや修正）が入っている | 変更の理由を後から追えなくなる |
| 6 | `AGENTS.md` の「制約」に収まっているか | ユーザと合意した前提を崩さないため |

指摘ごとに求める出力: **対象（ファイルと行）/ 何が問題か / 起きること / 根拠（コードや出力の引用）/ 重大度 / 確信度**。

## 3. 指摘を検証して採用する

偽の指摘はユーザの時間を奪い、レポート全体の信頼を落とす。**確信の高いものだけを採用する。**

採用しないもの:

- この PR が持ち込んだのではない既存の問題。ただし、この PR の変更によって表に出て動かなくなるものは採用する。
- 好み（命名、書き方の流儀、抽象化の度合い）。
- リンターやフォーマッタで分かるもの。

採用の前に、**指摘ごとに別のサブエージェント**（`researcher`、読み取り専用）へ、指摘と該当コードだけを渡して成り立つかを検証させる。次のいずれかを確かめられたものだけを採用する。

- 問題が起きる条件と結果を、コードから追って示せる。
- 再現するテストや実行の出力がある。
- 手順違反（証跡なし、設計文書の未更新など）を、文書と差分で示せる。

## 4. 修正して再レビューする

1 指摘 1 コミット。修正は `implementer` に、指摘・該当箇所・期待する結果を渡して委譲する。

- 作業前に `git branch --show-current` を確かめる。main なら止まってユーザに確認する。
- コミットメッセージは `fix: <何を直したか>` とし、本文に指摘の番号（F1 など）を書く。レポートと突き合わせられるようにするため。
- バグの修正には、同じ問題を捕まえる回帰テストを足す。
- 証跡の無い「合格」は、自分で実行して証跡を取り直すか、`未検証（理由）` に直す。
- 修正したら手順 2 からもう一度レビューする。修正が別の問題を作ることがある。

**上限は 3 周。** 次の 3 種類の指摘は直さない。「未解決」として、理由とともにレポートの「指摘と修正」（`findings`）と「残っていること」（`remaining`）に残す。黙って落とさない。

- 3 周しても収束しない（直すと別の問題が出る、原因が絞れない）。
- 判断が必要（仕様の選択、文言、優先度）。エージェントが決めると、承認済みの内容と食い違う。
- Acceptance Criteria の変更が必要。条件はユーザと合意したもので、実装側の都合では変えない。

## 5. レポートを作る

1. `references/report-guide.md` を読む（章ごとの書き方、差分の入れ方、スクリーンショットの撮り方）。
2. `assets/report-template.html` を `docs/plans/issue<N>/report.html` に複製し、プレースホルダー `{{…}}` を埋める。章の順序・id（`summary` `ticket` `where` `changes` `acceptance` `findings` `remaining`）・CSS は変えない。
3. 差分は `scripts/diff-html.mjs` で入れる。「変更の内容と差分」（`changes`）には変更のまとまりごとの差分（指摘のある行に印を付ける）、「指摘と修正」（`findings`）には指摘ごとの修正の差分。どちらも折りたたまれた状態で入る。
4. ガイドの「提出前の確認」を通す。

レビューを周回したら、追記せずに**作り直す**。継ぎ足すと古い記述が残り、数が合わなくなる。

## 6. 読み手テストをする

書いた本人には必ず読めてしまう。新規コンテキストのサブエージェントに `report.html` だけを渡し（リポジトリの他のファイルは読ませない）、次の 4 問に答えさせる。

1. このチケットの目的は何か。
2. 全体のどこを変えたか。
3. レビューの指摘は何で、どう直したか。
4. ユーザに残る作業は何か。

答えられない、または誤った箇所を直す。情報を足す前に、まず伝わる書き方に直す（長いレポートは読まれない）。直したら、別のサブエージェントでもう一度試す。2 回で通らなければ、通らなかった問いをユーザへの報告に書く。

## 7. GitHub に反映する

1. レポートと修正コミットを PR のブランチに push する。
2. PR 本文の末尾にレビュー結果を足す（`gh pr edit <PR> --body-file <一時ファイル>`）。既存の本文は消さない。

   ```markdown
   ## レビュー結果

   [レビューレポート](docs/plans/issue34/report.html)（HTML。GitHub 上ではソースが表示されるので、ローカルで開く）

   - 判定: ユーザの作業待ち
   - 未解決: F2 上限に達したときの文言（判断が必要）
   ```

3. `--comment` があるときだけ、採用した指摘の一覧（番号・対象・何が問題か・状態）を `gh pr comment <PR> --body-file <一時ファイル>` で投稿する。レポートの全文は貼らない。
4. マージはしない。マージはユーザの判断。

## 8. ユーザに報告する

短く、結論から。詳細はレポートにあるので繰り返さない。

1. **結論**: マージ可 / ユーザの作業待ち / 未解決あり
2. **レポートのパス**: `docs/plans/issue<N>/report.html`
3. **未解決の指摘**: 番号と 1 行。無ければ「なし」
4. **ユーザに残る作業**: 判断が必要なこと、ユーザしか実行できない検証（コマンドつき）。無ければ「なし」

## してはいけないこと

- 自分でレビューして済ませる。
- 確信のない指摘を「念のため」載せる。指摘が無いのにコードを書き換える。
- 未解決の指摘を黙って落とす。Acceptance Criteria を書き換えて「合格」にする。
- 実行した出力が無い行を「合格」と書く。
- テンプレートを使わずにレポートを書き起こす。章の順序・id・CSS を変える。
- main へ直接コミットする。PR をマージする。`--comment` なしで PR にコメントする。
