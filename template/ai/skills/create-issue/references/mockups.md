# 完成イメージの作り方

`create-issue` の手順 4 で、完成イメージを作ると決めたときに読む。目的は、ユーザが頭の中の絵とあなたの理解を見比べ、違いを起票前に言えるようにすること。決定が見えれば足りるので、作り込まない。

## 画面の変更: HTML モックアップ

CSS も含めて 1 ファイルに収め、外部のスクリプト・スタイルシート・Web フォント・画像を参照しない。`open` するだけで見られるようにするため。

- **実際の文言を入れる。** 文言も承認してほしい決定の一部。ダミーのラベルでは判断できない。
- **データは現実的な量にする。** 3 行の表では、100 行になったときの問題が見えない。
- **状態ごとに並べる。** 「操作前」「操作後」「該当 0 件」を見出し付きで縦に並べる。JavaScript で動かすより見落としが少ない。
- **変える部分だけを作る。** 変えない周辺は、枠と短いラベルで示す。

`AGENTS.md` にデザインシステムの指定があれば、それに従う。無ければ、色数を抑えた素直な見た目にする。凝ったデザインは、議論の焦点を決定からデザインへ移してしまう。

## 構成・データの流れの変更: 変更前後の図

変更前と変更後を必ず並べる。変更後だけでは、何が変わったのか伝わらない。形式は、Mermaid を含む Markdown（GitHub 上で描画されるので Issue から参照しやすい）か、インライン SVG を埋めた HTML。

- 箱の名前は、コンポーネント名ではなく読み手が知っている呼び方にする（「管理画面」「利用者 API」）。
- 矢印には、何が流れるかを書く（「利用者一覧」「認証トークン」）。
- 変わった箱と矢印だけを強調する。
- 1 図に 10 箱程度まで。超えるなら Issue が大きすぎる兆候なので、分割を検討する。

## 挙動・API の変更: 例かプロトタイプ

まず、リクエストとレスポンスの例で足りるか考える。足りるなら、それが最も速く読める。

```
GET /admin/users?sort=last_login_at&order=desc

200 OK
{
  "users": [
    { "email": "a@example.com", "last_login_at": "2026-09-18T02:11:00Z" },
    { "email": "b@example.com", "last_login_at": null }
  ]
}
```

境界の例を 1 つ入れる（上の `null` のような値が無い場合、上限、エラー応答）。境界は後で揉めやすく、文章だけでは合意できない。

体感速度や入力の受け取り方のように、例では判断できないときだけ、1 ファイルで動く最小のプロトタイプを作る。依存は追加せず、`docs/plans/` の外に実装を置かない。
