# create-issue

依頼: $ARGUMENTS

Issue は、ユーザと合意する唯一の設計文書。後段の `/implement-issue` は計画の合意を待たずに PR まで進むので、ここで取り違えた前提は PR になるまで表に出ない。

ユーザはコードベースもあなたの調査内容も把握していない。判断の負担を次の 3 つで引き受ける。

- **事実は自分で調べる。** コード・設計文書・既存 Issue から分かることは聞かない。聞くのは決定だけ。
- **質問には推奨回答と理由を添える。** ユーザが「推奨どおり」と一言で返せるようにする。
- **文章で伝わらないものは見せる。** 画面の並びや遷移は、文章だと合意したつもりになりやすい。

## 実行環境

- `$ARGUMENTS` は、起動時にスキル名の後ろへ続けた文字列。Codex では展開されないので、ユーザの入力から同じものを読む。
- `references/` は、この `SKILL.md` のあるディレクトリ（`ai/skills/create-issue/`）から辿る。
- サブエージェントは、名前付きのもの（`researcher` など）が無ければ汎用のものを使う。モデルと effort は `AGENTS.md`「タスクの実行」に従い、別の CLI を起動して委譲することはしない。

## 進め方

1. 調べる → 2. 規模を決める → 3. 質問する → 4. 完成イメージを見せる → 5. Issue を書く → 6. 承認をもらう → 7. 起票する → 8. 報告する

小さな修正なら 3 と 4 を省く。

## 1. 調べる

質問を作る前に読む: 依頼に関係するコード、`docs/architecture/`（設計の正本）、`docs/plans/`（過去の計画と検証記録）、既存の Issue（`gh issue list --state all --limit 50`、当たりがあれば `gh issue view <N>`）。範囲が広ければ `researcher` に委譲する。

**重複する Open Issue を見つけたら、先に知らせる。** 番号と題名を示し、新しく起票するか既存の Issue に足すかを聞く。

### 依存関係

open の Issue を読み、新しい Issue について 2 方向を判定する。依存関係も事実なので自分で調べ、ユーザには判定の確認だけを推奨つきで求める。

- **Blocked by**: 完了を待つ必要がある Issue
- **Blocks**: この Issue の完了を待つことになる Issue

依存と言えるのは、相手の変更が無いと成り立たないときだけ（相手が作る設計・データ構造・コードを前提にする）。同じ画面や同じ領域を触るだけなら依存ではない。依存を張りすぎると、並列で進められる作業が直列になる。各判定には根拠を一言添える（例: 「#30 が追加する管理者権限の判定を前提にするため」）。

判定したら、open の Issue 全体を 2 群に分けた**実行順序の表**を作る。ユーザが、いま並列で進められる作業を一目で分かるようにするため。

```
| 状態 | Issue |
| --- | --- |
| いま着手できる（並列） | #30 管理者の招待 / #31 監査ログの保存期間 / 今回の Issue |
| 待ち | #32 招待メールの文面（#30 を待つ） |
```

依存が循環していたら、実行順序が決まらないので指摘する。どちらかの依存を外すか、待つ部分を別 Issue に切り出す案を添える。

## 2. 規模を決める

依頼の規模に手順を合わせる。小さな依頼に多くの質問や完成イメージを出すと、それ自体が負担になる。判定は一言でユーザに伝える（ユーザは覆せる）。

| 規模 | 見分け方 | 質問 | 完成イメージ |
| --- | --- | --- | --- |
| 小さな修正・バグ | 変わる振る舞いが 1 か所。画面の見た目も API の形も変わらない | 0〜2 問 | 作らない |
| 通常の機能 | 1 PR で実装・検証・文書更新まで終わる | 1〜2 ラウンド | 迷いが残る箇所だけ |
| 1 PR に収まらない | 複数の層や画面にまたがり、検証の単位が分かれる | 親の目的に絞って 1〜2 ラウンド | 全体像を 1 枚 |

バグは `.github/ISSUE_TEMPLATE/bug.yml`、それ以外は `task.yml` の項目で書く。

## 3. 質問する

- 冒頭に、調べて分かった前提を 2〜3 行で示す。ユーザは調査内容を知らないので、これが無いと質問の意味が伝わらない。
- いま答えられる質問だけを出す。他の回答で意味が変わる質問は、次のラウンドに回す。
- 番号を振り、各問に推奨回答と 1 行の理由を付ける。理由は質問の言い換えではなく、なぜそれを勧めるか。
- 選択肢は 2〜3 個に絞る。1 ラウンドは 5 問まで。
- 依存関係の判定も、推奨つきの 1 問として確認する。

回答を待つあいだは、判断に必要な最小の完成イメージ（仮案と明示する）と質問だけを出して終える。Issue 本文の全文は、回答が揃ってから書く。

```
調べたこと
- 管理画面の利用者一覧は登録日の降順で固定。並べ替えの UI はまだない。
- 一覧は管理者 API の 1 リクエストで全件返している（現在 200 件程度）。
- 重複する Open Issue はなし。open の #30・#31 は別の画面を触るので、並列で進められます。

規模: 通常の機能。1 PR に収まる想定です。すべて推奨どおりなら「推奨どおり」で構いません。

Q1. 並べ替えの対象にする列
    (a) 最終ログイン日のみ  (b) 登録日・最終ログイン日・メールの 3 列
    推奨: (a)。目的は「休眠アカウントを見つける」ことなので、1 列で足ります。

Q2. 並べ替えの実行場所
    (a) サーバ側  (b) ブラウザ側
    推奨: (b)。全件を 1 リクエストで返している今の作りなら API の追加が不要で、変更が一覧画面だけに収まります。

Q3. 依存関係
    推奨: Blocked by なし、Blocks なし。一覧画面だけで完結し、#30（管理者の招待）とは触る画面が別です。
```

### プロジェクトの制約

`AGENTS.md` の「制約」（費用の上限、使える技術の範囲など）を読む。制約に触れ得る要望は、気づいた時点で指摘する。起票してしまうと `/implement-issue` が実装の手前で止まり、そこまでの作業が無駄になる。

- どこが制約に触れるかを具体的に述べ、確かめていない数値（料金、枠など）は断定しない。
- 制約の範囲内に収める代替案を推奨つきで示し、超えることを承知で進めるかはユーザに確認する。該当する要件を黙って外さない。

## 4. 完成イメージを見せる

作るのは、見た目・並び・文言・遷移を思い浮かべないと答えられない決定が残っているとき。決定が文章で一意に伝わるなら作らない（小さな修正、バグ、内部実装だけの変更、文書だけの変更）。迷ったら 1 つだけ作り、1 Issue につき 2 つまで。

| 変わるもの | 作るもの |
| --- | --- |
| 画面 | 単一ファイルの HTML モックアップ（外部依存なし） |
| 構成・データの流れ | 変更前後を並べた図（Mermaid か インライン SVG） |
| 挙動・API | リクエストとレスポンスの例、または最小のプロトタイプ |

置き場所は `docs/plans/_draft-<slug>/`（Issue 番号が決まったら手順 7 で改名する）。`<slug>` は依頼を表す英小文字 2〜4 語をハイフンでつなぐ（例: `user-list-sort`）。作り方は [references/mockups.md](references/mockups.md) を読む。

ユーザには、パスに加えて開き方と見てほしい箇所を伝える。パスだけでは見てもらえない。

```
完成イメージを置きました: docs/plans/_draft-user-list-sort/list.html
`open docs/plans/_draft-user-list-sort/list.html` で開けます。見てほしいのは、並べ替えの見出しの位置と、最終ログインが無い利用者の表示（ページ下部）です。
```

## 5. Issue を書く

**見出し**は、対象テンプレート（`task.yml` か `bug.yml`）の各項目の `label` を、ファイルの順に `### <label>` として並べる。必須かどうかは `validations: required: true` で分かる。項目名をこのスキルに写さないのは、テンプレートを直したときに食い違わないようにするため。

**振る舞いと理由で書く。** 書くのは「誰が何をできるようになるか」と「なぜ必要か」。ファイルパス・行番号・関数名は実装が進むと古くなるので書かない。実装方法は `/implement-issue` が計画で決める。例外は、データの形・状態の遷移・API の形のように、断片を載せたほうが決定を正確に表せるとき。

**Acceptance Criteria** は 1 行 1 条件で、読んだ人が確認方法を思い浮かべられる形にする。

| 悪い例 | 理由 | 良い例 |
| --- | --- | --- |
| 管理画面が使いやすくなっている | 合否を判定できない | 管理者は利用者一覧を最終ログイン日の降順・昇順に並べ替えられる |
| `backend/src/admin.ts` の一覧取得を直す | 場所の指示で、振る舞いが分からない | 権限のない利用者が管理 API を呼ぶと 403 が返り、監査ログに 1 件記録される |
| テストを追加する | 何が守られるのか分からない | 再現テストが修正前に失敗し、修正後に成功する |

完成イメージがあれば、該当する条件から参照する（例: 「並べ替え後の一覧が完成イメージ `list.html` の表示と一致する」）。参照が無いと、承認したイメージが合否の基準にならない。

**Blocked by** の節が依存関係の正本。どのエージェントも `gh issue view` だけで実行順序を判断できる。待つ Issue を理由つきで並べ（`- #30 追加される管理者権限の判定を前提にするため`）、無ければ「なし」と書く。空欄だと、判定していないのか依存が無いのか区別できない。この Issue の完了を待つ相手（Blocks）はここに書かず、相手の `Blocked by` に書く（手順 7）。両側に書くと片方だけ直されて食い違う。

**Open Questions** は空にして起票する。残すのは答えが実装を妨げないと言い切れるときだけで、その理由も書く。答えで実装の方向が変わる問いは、手順 3 に戻って聞く。

### 1 PR に収まらないとき

単独で動かして検証できる単位の子 Issue に分ける。各子 Issue は、狭くても入口から出口まで通って動くものにする。DB だけ・API だけのように層で分けると、どの子も単独では動かず、検証と PR が 1 対 1 で対応しなくなる。

- 親 Issue には目的と子の一覧を、子 Issue には親への参照を書く。
- 子どうしの依存関係を判定し、並列で進められる組と、最初に着手する 1 件（とその理由）を示す。
- 分割案を先に見せ、粒度と並列の組を確認してから本文を書く。
- 起票は親が先。続けて、待つ相手のいない子から順に起票する（後続の `Blocked by` に番号が要るため）。

## 6. 承認をもらう

承認の前に `gh issue create` を実行しない。起票は外向きの操作で、Issue はユーザとの合意文書になる。

見せるもの: 題名、**本文の全文**（要約ではない）、完成イメージのパスと見方、起票後の実行順序の表、他の Issue に加える変更（相手の `Blocked by` への追記）。既存の Issue を黙って書き換えると、ユーザの知らない実行順序ができる。

```
この内容で起票してよいか確認をお願いします。

題名: 管理画面の利用者一覧を最終ログイン日で並べ替えられるようにする

本文:
---
（全文。`### Blocked by` を含む）
---

完成イメージ: docs/plans/_draft-user-list-sort/list.html
他の Issue への変更: #33 の Blocked by にこの Issue を追加します（並べ替えの UI の上に絞り込みを足すため）。

（起票後の実行順序の表）

「承認」で起票します。直したい箇所があれば、その部分だけ教えてください。
```

差し戻されたら、指示された箇所だけを直して同じ形で再提示する。冒頭に直した箇所を 1〜2 行で書き、完成イメージも新しい範囲に合わせる。再提示は承認ではないので、起票もフォルダの改名もしない。

## 7. 起票する

1. 本文をファイルに書き出し、`gh issue create --title "<題名>" --body-file <パス>` で起票する（`--body` に直接渡すと改行やバッククォートが崩れる）。
2. 完成イメージがあれば、フォルダを `mv docs/plans/_draft-<slug> docs/plans/issue<N>` で改名し、ブランチにコミットして push する。作業ツリーに他の未コミットの変更があるときは、ブランチを作らずユーザに確認する。

   ```
   git fetch origin
   git switch -c issue-<N>-<slug> origin/main
   git add docs/plans/issue<N>
   git commit -m "docs: add design mockups for issue <N>"
   git push -u origin issue-<N>-<slug>
   ```

3. push のあと、Issue 本文に完成イメージへのリンクを足す（`gh issue edit <N> --body-file <パス>`）。リンクは `https://github.com/<owner>/<repo>/blob/issue-<N>-<slug>/docs/plans/issue<N>/<ファイル名>`。`<owner>/<repo>` は `gh repo view --json nameWithOwner -q .nameWithOwner` で得る。
4. この Issue の完了を待つ相手がいれば、相手の `### Blocked by` に 1 行足す。`gh issue view <相手> --json body -q .body` で本文を取り、その節に 1 行足して `gh issue edit <相手> --body-file <パス>`。本文の他の部分は変えない。
5. 依存関係を GitHub の issue dependencies にも登録する。Issue の画面に依存が表示されるようになる。正本は本文の `### Blocked by` なので、登録に失敗しても止まらず、理由を報告に書く。

   ```
   REPO=$(gh repo view --json nameWithOwner -q .nameWithOwner)
   BLOCKER_ID=$(gh api repos/$REPO/issues/<待つ相手の番号> --jq .id)
   gh api --method POST -H "X-GitHub-Api-Version: 2026-03-10" \
     repos/$REPO/issues/<待つ側の番号>/dependencies/blocked_by -F issue_id=$BLOCKER_ID
   ```

   - 登録は「待つ側の Issue に、待つ相手を足す」の 1 方向。新しい Issue が待つ相手と、新しい Issue を待つ相手のそれぞれについて実行する。
   - 渡すのは Issue 番号ではなく `id`（内部の数値 ID）。整数で送るため `-f` ではなく `-F` を使う（`-f` は文字列になり 422 が返る）。
   - `gh api repos/$REPO/issues/<N>/dependencies/blocked_by --jq '.[].number'` で、本文の `### Blocked by` と一致することを確かめる。

## 8. 報告する

短く。Issue の番号と URL、依存関係に加えた変更、完成イメージの場所、実行順序の表、次の一手。

```
Issue #34 を起票しました: https://github.com/<owner>/<repo>/issues/34
依存: なし。#33 の Blocked by に #34 を追加しました。
完成イメージは issue-34-user-list-sort ブランチの docs/plans/issue34/ にあります。

| 状態 | Issue |
| --- | --- |
| いま着手できる（並列） | #30 / #31 / #34 |
| 待ち | #32（#30 を待つ）/ #33（#34 を待つ） |

次: /implement-issue 34
```

## 起票前の確認

- [ ] テンプレートの必須項目が埋まっている
- [ ] Acceptance Criteria が 1 行 1 条件で、各行の確認方法を思い浮かべられる
- [ ] Open Questions が空（残すなら、実装を妨げない理由がある）
- [ ] `### Blocked by` に、待つ Issue と根拠、または「なし」がある。依存が循環していない
- [ ] 本文に、古くなるファイルパスや行番号が無い
- [ ] 完成イメージがあれば、Acceptance Criteria から参照している
- [ ] `AGENTS.md` の「制約」に触れる要望が残っていない
- [ ] 1 PR に収まる。収まらないなら、単独で検証できる子 Issue に分けてある
- [ ] ユーザの承認を得た
