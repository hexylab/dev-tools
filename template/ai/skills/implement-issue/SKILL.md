# implement-issue

Issue 番号: $ARGUMENTS（以下 N。N が 28 なら、作業文書は `docs/plans/issue28/`、ブランチは `issue-28-<slug>`）

承認済みの Issue 1 件を PR まで運ぶ。人が判断するのは Issue の承認と PR のマージだけなので、その間は自分で決めて進める。ユーザはコードベースも調査内容も把握しておらず、途中で確認を求めても判断材料の無いまま待たせるだけになる。

- **止まらない。** 設計の選択、命名、計画からの逸脱は自分で決め、理由を `plan.md` に書く。止まるのは [止まる条件](#止まる条件) の 4 つだけ。
- **証拠のない完了を主張しない。** 受け入れ条件を「合格」にできるのは、このセッションで確認コマンドを実行し、出力を読んだ行だけ。

## 実行環境

- `$ARGUMENTS` は、起動時にスキル名の後ろへ続けた文字列。Codex では展開されないので、ユーザの入力から同じものを読む。
- サブエージェントは、名前付きのもの（`researcher`・`implementer`・`implementer_lite`・`reviewer`）が無ければ汎用のものを使う。モデルと effort は `AGENTS.md`「タスクの実行」に従い、別の CLI を起動して委譲することはしない。
- サブエージェントの「できました」は証拠ではない。差分と実際の出力で確かめる。全体の進行と最終的な品質は自分の責任。

## 止まる条件

次の 4 つはユーザにしか決められない。該当したら手を止めて判断を求める。

1. **`AGENTS.md` の「制約」（費用の上限など）を超える見込みがある。** 制約を外す決定はユーザのもの。確かめていない料金や枠の数値は断定しない。
2. **破壊的な操作、または共有環境に影響する操作が必要になる。** 本番データの変更・削除、デプロイ済み環境への反映、共有ブランチへの push など。
3. **Acceptance Criteria 自体を変える必要がある。** 前提が崩れていた、条件どうしが矛盾している、技術的に成立しない、など。
4. **`Blocked by` の Issue が open のまま。** 前提が未完成のまま実装すると、作り直しか競合になる。待っている Issue の番号と題名、待つ理由を示し、先にそちらを `/implement-issue` する案を出す。先行 Issue をこの作業の中で実装して回り込まない。ユーザが「それでも進める」と明示したら進め、その判断を `plan.md` の「仕様」表に記録する。

止まるときは、次の 3 点を 1 つの報告にまとめる。手順どおりの停止であり、ユーザが次に何をできるかが分かればよい。

- 何が分かったか（読んだファイルや Issue など、根拠つき）
- 選択肢と、それぞれの結果
- 推奨とその理由

Acceptance Criteria を書き換えたり、満たしたことにしたりしない。Issue と PR の対応が崩れ、変更の理由を後から追えなくなる。

## 1. Issue と既存の作業を読む

```bash
gh issue view N --comments
ls docs/plans/issueN/ 2>/dev/null
```

- コメントには、本文に反映されていない合意が入ることがあるので一緒に読む。
- 本文の `### Blocked by` が依存関係の正本。挙がっている Issue を 1 件ずつ `gh issue view <番号> --json state,title` で確かめ、open があれば止まる条件 4。
- `docs/plans/issueN/` の完成イメージ（モックアップ・図・プロトタイプ）は、ユーザが承認した見た目と挙動の正本。実装はこれに合わせる。
- `plan.md` が既にあれば中断された作業。冒頭の「状態」と「受け入れ条件の検証」表を読み、済んだ行と既存の証跡は残して続きから進める。

## 2. ブランチ

```bash
git fetch origin
git branch -r --list 'origin/issue-N-*'
```

見つかれば checkout して引き継ぐ（`create-issue` が完成イメージを push している）。無ければ `git switch -c issue-N-<短い英語の slug> origin/main`。main へは直接コミットも push もしない。

## 3. 調査

読むもの: 変更する範囲のコード、`docs/architecture/`、関連する過去の `docs/plans/`、外部サービスの仕様。範囲が広ければ、調べる対象と知りたいことを明示して `researcher` に委譲する。

外部のサービスやライブラリの仕様は記憶で書かず、公式ドキュメントで確認して URL とバージョンを記録する。

後から根拠を追う価値のあるもの（外部仕様の引用、測定値、採らなかった案と理由）だけを `docs/plans/issueN/research.md` に残す。

## 4. 計画

`docs/plans/TEMPLATE.md` を読み、それに従って `docs/plans/issueN/plan.md` を書く。

- **2 つの表**（「課題と目的への対応」「受け入れ条件の検証」）には、Issue の Problem・Goal・Acceptance Criteria を 1 項目 1 行で、原文のまま漏れなく転記する。レビューで Issue と 1 行ずつ突き合わせるため。
- **確認方法は実装前に決める。** 実装後に決めると、通ると分かっている方法を選んでしまう。
- **設計判断は理由とともに「仕様」表に書く。**「未決」にするのは、ユーザにしか決められない論点だけ。
- 状態を `実装中` にし、ユーザの合意を待たずに実装へ進む。Issue の承認が計画の前提。

`plan.md` の「状態」は節目（`計画中` → `実装中` → `検証完了`）で更新する。コンテキストが尽きても、別のセッションがこの行と検証の表から続きを進められる。

## 5. 実装

設計判断を伴うものは `implementer`、手順が明確なものは `implementer_lite` に委譲する。

- テストは対象のコードのそばに置く。複数の部分にまたがるものだけルートの `tests` に置く。
- 既存の規約（命名、エラー処理、テストの置き方）に合わせる。
- 不要な機能追加・リファクタ・抽象化をしない。範囲外で気づいたことは直さず、PR 本文か次の Issue の提案に回す。
- 計画から外れたら、その変更と一緒に `plan.md` を直す。
- 設計が変わるなら `docs/architecture/` を、セットアップ・デプロイ・運用の手順が変わるなら `docs/operations/` を、同じ PR で更新する。

## 6. 検証

受け入れ条件を 1 行ずつ、`plan.md` に書いた確認方法で検証する。

1. 確認コマンドを実行し、出力を読む。
2. コマンドと出力の要点を `docs/plans/issueN/validation.md` に残す。判断の根拠になる数値やエラーは省略しない。
3. `plan.md` の表に、結果と証跡（`validation.md` の該当箇所）へのリンクを書く。
4. リポジトリ全体の確認を通す（`AGENTS.md` や README に指定があればそのコマンド。無ければ型検査・テスト・build に当たるもの）。変更が小さくても省かない。

失敗したら原因を直して再検証する。確認方法を緩めて通ったことにしない。

ユーザしか実行できない検証（秘密の鍵が要る smoke、実機での確認など）では止まらない。その行を `未検証（理由）` とし、ユーザがそのまま実行できるコマンドを書いて先へ進む。秘密の値は推測せず、ファイルにも書かない。

終わったら状態を `検証完了` にする。

## 7. PR の前のレビュー

新規コンテキストのサブエージェント（`reviewer`）に差分を読ませる。渡すのは、差分の範囲（`git merge-base origin/main HEAD` から `HEAD` まで）、`plan.md` のパス、Issue 番号だけ。会話履歴は渡さない。自分で書いたコードは思い込みごと読んでしまうので、経緯を知らない目に読ませる。サブエージェントを使えない環境では、未実施とその理由を PR 本文に書く。

妥当な指摘を直し、1〜2 周で切り上げる（本格的なレビューは別セッションの `review-pr` が行う）。採らなかった指摘は、理由を `plan.md` に残す。

## 8. PR

コミットして push し、`.github/pull_request_template.md` に従って `gh pr create` する。

- `Closes #N`
- **変更内容**: 何を、なぜ。経緯を知らない人が短時間で読める長さで。
- **受け入れ条件の検証結果**: `plan.md` の表と同じ行構成で、結果と証跡へのリンク。
- **ユーザに残る作業**: `未検証` の項目と、実行するコマンド。無ければ「なし」。
- **計画から外れた点**: 変更と理由。無ければ省く。

`plan.md` の「完了の確認」にチェックを付ける。満たせない項目はチェックせず、理由を PR 本文に書く。

## 9. 報告

- PR の URL
- 受け入れ条件の結果（合格 n 件 / 未検証 n 件と、その理由）
- ユーザに残る作業
- 次の一手: 別のセッションで `/review-pr <PR 番号>`

`review-pr` は自分で呼ばない。実装の経緯を知るセッションがレビューすると、見落としを「意図どおり」と正当化しやすい。

## 迷いやすい場面

| 場面 | すること |
| --- | --- |
| 設計を決めきれない | ユーザにも判断材料は無い。決めて、理由を `plan.md` に書く |
| 計画の合意を取りたくなった | Issue の承認が計画の前提。待たずに進む |
| Acceptance Criteria が厳しい、または矛盾している | 書き換えずに、止まる条件 3 で確認する |
| `Blocked by` の Issue はもう終わっているはず | 推測せず、`gh issue view` で状態を確かめる |
| 秘密の鍵が要る検証がある | 止まらない。`未検証（理由）` とコマンドを書いて進む |
